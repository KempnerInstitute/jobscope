What it is

A command-line report on Slurm job efficiency. jobscope decodes the CPU, memory, GPU and GPU-memory utilization Slurm already stored in each job's sacct record, adds the DCGM and NVML profiling series from Prometheus, bands every number, and names the jobs that wasted their allocation — one bulk query for a whole selection, and terminal charts for when an average is not the answer.

Design rules
  • Report what was recorded, never recompute it. A finished job's utilization is the number Slurm stored, so every view agrees.
  • Measured time, not wall clock. An exporter that went quiet leaves a gap, not an idle job.
  • Every column names its source. The header block says which record or exporter answered.
  • Withhold rather than guess. Too few scrapes and the verdict is declined; no source and the cell prints -.
  • No silent caps. A selection past a few thousand jobs warns, names the narrowings you are not using, then proceeds.
  • Site policy is code. The tuned config is tracked in the repository and changes through pull requests.
What you get
One bulk query

CPU/MEM/GPU/GMEM match jobstats job for job, from a single sacct call rather than one per job.

Summary by metric

USED is resource-time that did work over what was allocated, beside GOOD/OK/BAD counts per metric.

Problem jobs

The jobs in a selection that crossed the configured waste thresholds, named and ordered worst first.

Time series

One CSV row per GPU per scrape; --plot-ts charts a panel per metric, --plot-ts-overlay a panel per GPU.

Triage and verdicts

--eff sorts a whole partition into categories; --verify answers whether one job is idle, and since when.

Site bring-up

probe reports what Slurm and Prometheus expose here; probe --init writes a config from those findings.

What Slurm actually stored

The AdminComment field holds JS1: followed by base64-encoded gzipped JSON: per node cpus, total_time, used_memory, total_memory, and the per-GPU maps gpu_utilization, gpu_used_memory and gpu_total_memory — keyed by minor_number as a string. Decoding it is why one query answers for a whole selection.

The report says so, per column
# a finished job, read back Source: CPU% MEM% GPU% GMEM_GB GMEM_TOTAL_GB <- jobstats; SM_ACT% TENSOR% DRAM% POWER_W <- dcgm # the same job while it runs, measured Source: CPU% MEM% <- cgroup; GPU% GMEM_GB SM_ACT% TENSOR% DRAM% POWER_W <- dcgm
A running job has no stored record — Slurm writes it at job end — so its numbers are always measured, and the line says so. That is also the expensive case: the runtime average costs about one query per job per metric, where --instant is one query per metric for the whole selection.
Preference order — one source of truth per number, chosen by job state
job stateCPU% MEM% GPU% GMEM%other DCGM columns
finished, summary presentthe jobstats summary, alwaysPrometheus
finished, summary absent or JS1:ShortblankPrometheus
runningPrometheus, shaped as a summaryPrometheus
A finished job's utilization is never recomputed. The summary is what Slurm recorded, so every view reports the same number and re-deriving it would reintroduce the boundary disagreement that makes a recomputed window drift on short jobs.
Naming a source promotes it for the columns it can serve — --gpu-source dcgm keeps GPU memory, which DCGM has no total for here; --gpu-source nvml does narrow the table, since that exporter publishes no SM, tensor or DRAM activity at all. Defaults live in [gpu] source and [host] source. A column whose source has nothing prints -.
The two sources were checked against each other. --no-jobstats reads the same four columns from Prometheus for finished jobs too. Across 51 jobs spanning CPU-only, single-GPU, multi-GPU and multi-node shapes they agree to within one point — the memory columns exactly.

1
A self-contained header

User, account, partition and window are unconditional — an axis you did not narrow reads (all accounts) rather than going blank, so saved output still says what it covered.

2
One row per job

Percent columns are averages over the whole allocation. PARTITION and GPU_TYPE say where the job ran and on what card, so a selection spanning partitions can tell its rows apart.

3
Waste, located and measured

USED is resource-time that did work over what was allocated. The bands locate waste; USED measures it — no red jobs but a low USED means every job wastes a little.

4
Busy, computing nothing

Here: 8 H100s held at 28% duty cycle with 6% SM residency and 3% tensor. The card was occupied; the pipes were idle. That is the gap a single number hides.

Thresholds

Five bands, two tables, per metric

red yellow green
wasteful< 2%
inefficient2 – 10%
needs improvement10 – 20%
average20 – 40%
good> 40%
The edges are not uniform. "Below 2%" excludes 2, while every band above includes its top: 10.0 is inefficient, 10.1 needs improvement. Edges must not decrease within a metric once resolved against the defaults — jobscope rejects a config where they do, and jobscope config prints both tables as they resolve. And green is not efficient: average is 20–40% of an allocation doing work. The bands are a triage scale for finding waste, not a grade sheet.
Two tables, and nothing is inherited between them
[thresholds.summary.wasteful] default = 2 cpu = 5 # a GPU job idling its cores is normal; 2% would flag them all [thresholds.timeslice.wasteful] default = 2 cpu = 8 # a short window dips further than a whole-job average [thresholds] power_w = 100 # POWER_W, in WATTS -- below this a GPU counts as idle
[thresholds.summary] grades the plain report — one average over the whole runtime. [thresholds.timeslice] grades --ts, --plot-ts and --eff, where samples are pooled inside a window. A two-hour slice catching a checkpoint pause is not a two-hour idle job, so neither table inherits from the other.
Edges are per metric, because the metrics do not mean the same thing: a GPU job legitimately holds cores it never uses, so CPU% at 4% is ordinary where GPU% at 4% is idle, and SM_ACT% sits structurally below GPU% on the same work. POWER_W has no bands at all — only a floor in watts, per GPU model, since idle draw is a property of the hardware.

When an average is not the answer

Keeping the shape of the run

An average cannot say whether a job used half a GPU throughout or all of a GPU for half the run. The time-series views keep one value per scrape.

Four views of the same series
--ts [WINDOW] One CSV row per GPU per scrape. Pipe it into jobscope plot, or keep it for anything else.
--ts --stats Summarize the window: min / mean / max / last per GPU and metric. --stats node and --stats job pool it upward.
--plot-ts One panel per metric, one column per GPU. The view to use without colour, since each series is drawn on its own axis.
--plot-ts-overlay One panel per GPU, every metric on a shared axis, one row per node — so it needs no --nodename.
The overlay answers the question behind most diagnosis: did the metrics move together? GPU% 90 beside SM_ACT% 8 on one pair of axes is a card that was occupied but barely loaded. Watts are left out, because they cannot share a scale with percentages.
On a multi-node job add --nodename to --plot-ts, or GPU ids from different nodes merge — GPU 0 exists on every node. --gpuid 0,1 narrows to particular cards.
jobscope -j 36788818_3 --ts --csv | jobscope plot
One panel per GPU, every metric on a shared axis, with min / mean / max / last beneath. GPU% averages 85.8 and SM_ACT% 70.0 while TENSOR% averages 2.1 — a card worked hard by kernels that never touch the tensor pipes.

Triage

--eff --verify
Which jobs, worst first
$ jobscope -p kempner_h100 --ts 10m --eff 142 jobs, by best of GPU%, SM_ACT%, OCC%, TENSOR%, DRAM% (POWER_W caps the verdict when idle) wasteful (GPU% <2%, SM_ACT% <2%, ...) 15 jobs JOBID NODES GPUS USER GPU% SM_ACT% POWER_W 36229482 1 2 bob 0.0 0.0 70 good (best of ...: >40%) 98 jobs (--eff all to list them)
Each heading states the rule it applied, so the criteria never has to be looked up. good collapses to a count by default — on a healthy partition it is most of the output and none of the point.
--eff rides on --ts WINDOW, so the categories are the timeslice bands rather than the whole-runtime ones. --csv gives one row per job, carrying GMEM% and POWER_W even though neither votes on the label: a row you will sort or join on should say what was measured.

--verify needs -j: it fetches every scrape of one job's series, which is right for a job you are about to scancel and wrong for a partition. --full adds where each metric's time went — a band split per metric, a timeline and per-unit idle split for each voting metric, and the per-rung ladder. On a one-GPU job that is 94 lines against 19.
Judged on its best metric

The same rule as "every metric is below X", read from the other end: GPU%, SM_ACT%, TENSOR%, DRAM%, CPU% — and CPU% can vote no higher than inefficient.

Two columns do not vote

GMEM% sits out: reserving 80 GB and computing nothing is still computing nothing. POWER_W is graded in watts against a per-model floor and can only lower a verdict.

Withheld, not guessed

Under 30 scrapes in the window, or fewer than half arriving, and no verdict is given. It is qualified when the metric moves faster than it is sampled, since no mean of such a series is reproducible.

Measured time only

Every duration is samples times the scrape interval, never the wall clock. The job line is the instants every unit was idle together, so an outage on one card is not the job being idle.

Bringing up a cluster

probe first, then policy in git

tracked git-ignored
probe reads your cluster and, apart from --init, writes nothing
probe Can jobscope reach Slurm and Prometheus, and how far back the data goes. Each check fails independently, so it is useful precisely when jobscope does not work yet.
probe --metrics Every series this server carries for a real job, marked ok, new or absent — the one to run before editing [metrics] or [thresholds].
probe --toml That listing as an editable [metrics] block. Stdout is only ever TOML and diagnosis goes to stderr, which makes >> jobscope.toml safe.
probe --coverage Host counts per series, grouped by source, and a missing section naming nodes that run jobs but do not publish — over five partitions here, 254 nodes reduced to the one worth acting on.
probe --init Writes a config from those findings, and refuses to overwrite one. It writes the git-ignored tier, not the reviewed one.
A committable config for an endpoint that needs a token
[prometheus] url = "https://prometheus.example.net/api/prom" # no secret -- safe to commit credentials_file = "secrets/prom_creds" # git-ignored; USER:TOKEN, one line
A relative path resolves against the config file's own directory. jobscope refuses a credentials file readable by group or other, one holding a whole URL, and a url that already embeds a credential. $JOBSCOPE_PROM_URL wins over both, and says so.
Where the config comes from — first match wins
1
jobscope -c PATH
one invocation
2
$JOBSCOPE_CONFIG
one shell, job, or module file
3
<repo>/config.toml
git-ignored — local experiments, and probe --init
4
<repo>/jobscope.toml
tracked — the site's policy, reviewed through pull requests
5
~/.config/jobscope/config.toml
a user with no checkout
Both repository tiers are found from jobscope's own position on disk, not the working directory — so cron, whose cwd is $HOME, and an sbatch script pick the site policy up with nothing set and no flag. jobscope config names the file that answered.
The layout is matched exactly, not walked upward for .git. A walk finds the nearest marker, and on a shared login node that is not necessarily ours: an empty /tmp/.git owned by another user — there is one on this cluster — would make /tmp the root, and jobscope would then read a config that user can write, naming the endpoint we authenticate to.

How it is kept honest
  • The import graph is asserted. A new module has to be classified in test_layering.py, or the boundary rules would skip it in silence.
  • The two sources were compared job for job. 51 finished jobs across four allocation shapes agree within a point; memory exactly.
  • Exporter gaps are diagnosed, not absorbed. probe --coverage is how a hole in a metric family is told apart from a bug here.
  • The bands are reviewed like code. Site policy sits in a tracked jobscope.toml, so retuning a threshold is a pull request.

Known limits — stated, because a silent one is worse
MIGNo DCGM columns on a MIG row, and no GPU% at all — NVML publishes no device duty cycle once a card is partitioned. The historical views collapse sibling instances; --ts is the accurate view.
clipDCGM columns cannot be clipped to GPU ownership, so a card that changed hands mid-window may include a neighbouring job's samples. The nvidia_* columns are clipped and do not have this problem.
costThe running view's runtime average costs roughly one query per job per metric — 628 against 12 on one 110-job partition. It is paced, not capped: rows print as they land. --instant or --min-elapsed are what reduce the count.
shortA recomputed window is boundary-sensitive on short jobs. The preference order avoids it for finished jobs; a running job has no stored summary to prefer.
scopeThe running view's ownership query is not scoped to a cluster, so a Prometheus serving several clusters could in principle collide on job ID.
